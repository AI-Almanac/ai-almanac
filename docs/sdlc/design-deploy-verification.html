Post-Deploy Verification

ai-almanac · design doc · CI-based deployment monitoring that survives a GCP→AWS migration
Design constraint: a cloud migration may be coming, so monitoring lives in GitHub Actions (stays) rather than Terraform-managed GCP alerting (throwaway). Cloud-specific commands are isolated in one script. This mirrors Anthropic's watch-telemetry-then-expand rollout posture: develop→staging is the small-group rollout, verification is the telemetry watch, promoting to main is the expansion.

The verify job

One new job appended to both deploy-staging.yml and deploy-prod.yml, running after the Cloud Run deploy step.

1Wait for revision readiness

Poll the service until the new revision serves 100% traffic and reports Ready (timeout 5 min). Catches image-boot and migration failures immediately rather than via user reports.

2Smoke testsCloud-agnostic
  • GET /health → 200 (endpoint exists in server/app.py)
  • 2–3 read-only API endpoints (e.g. regions list, models list, data-sources list) → 200 + sane JSON shape
  • SPA root loads → 200 with expected HTML marker

Plain curl against the public URL — nothing GCP-specific.

3Log scan (soak window)

Sleep ~5–10 min (staging only; prod can shorten), then pull ERROR-severity log entries for the new revision via scripts/post_deploy_check.sh. Threshold: any 5xx spike or new exception signature fails the job.

Pass  Deploy verified

Job summary records revision, smoke results, log counts. On develop: staging is your soak environment before promoting to main.

Fail  Workflow fails → notification

  • GitHub notifies on workflow failure (email/app — free, no new vendor)
  • AI optional triage step: Claude summarizes the deploy diff + captured error logs into the job summary — first-pass incident analysis, only spends quota on failed deploys
  • Human decision: fix-forward or rollback (runbook below)

Sketch

# appended to deploy-staging.yml (deploy-prod.yml identical, tighter soak)
  verify:
    needs: deploy
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<sha>
      - uses: google-github-actions/auth@<sha>        # existing WIF setup
        with: { workload_identity_provider: ..., service_account: ... }
      - name: Wait for revision + smoke test + log scan
        run: ./scripts/post_deploy_check.sh almanac-backend-staging "$BASE_URL"
      - name: AI triage on failure
        if: failure()
        uses: anthropics/claude-code-action@<sha>
        with:
          claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
          prompt: |
            The staging deploy for commit ${{ github.sha }} failed verification.
            Read logs/errors.txt and the commit diff. Summarize the most likely
            cause and whether rollback or fix-forward is appropriate.
            Write your analysis to the GitHub step summary.

Rollback runbook (documented, not automated)

  • Traffic rollback: gcloud run services update-traffic <svc> --to-revisions <prev-revision>=100
  • Migration caveat: migrations run before deploy, so a rolled-back revision runs against the new schema. Policy: migrations must be backward-compatible one version (additive first, destructive changes in a later release).
  • Automated rollback is deliberately out of scope — solo project, low deploy volume; a human decision beats a flapping automation.

Rejected alternatives

OptionWhy not now
Terraform-managed GCP alert policies / uptime checksCheapest today but discarded on AWS migration; violates the portability constraint.
Sentry error trackingBest long-term signal and fully portable — deferred to Phase 4 (first real users), not rejected.
External uptime pinger (healthchecks.io etc.)Cheap and portable, but catches only total downtime; the verify job catches the more common bad-deploy case. Easy add later.
Scheduled always-on AI monitoring agentAnthropic-grade coverage, but continuous quota burn for a low-traffic service. The failure-triggered triage step captures most of the value.
